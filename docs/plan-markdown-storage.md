## 1. 目标与代价

**目标**：`.novel/novel.json` 退化为元数据仓库；小说内容（全书大纲、人物设定、世界观
设定、分卷大纲、章节大纲、章节细纲、章节正文）各自成为工作区里的独立 Markdown 文件，
人可以直接阅读、直接用编辑器修改。

**接受的代价**（用户已明确选择）：

1. **多文件没有单一事务**。现在的"一个 JSON 文档 + 一次 `replaceIfVersion` 原子写"变成
   多个文件的多步写入。缓解见 §6：内容文件先写、元数据后写，失败时报告"哪些文件已写、
   哪些没写"，绝不谎报成功。
2. **以文件为准，自动采纳**（用户选择）。人（或其它工具）改了 Markdown，即视为权威输入，
   工具读取时采纳并把索引刷新到 `novel.json`。
   **唯一的护栏**：文件**语法坏掉**时不算"采纳"，而是**报错并指名文件与原因**，
   绝不静默丢弃内容、也绝不用内存里的旧值覆盖它。采纳针对的是"能解析的文件"，
   不是"任何文件"。
3. **多一处分层**：`core/*` 的纯函数不变，但它们操作的 `NovelState` 由 store 从
   "元数据 + 一组 Markdown 文件"组装出来。组装/拆解逻辑集中在 store 与 codec。

### 2.1 命名规则

- 顶层五个文件名**固定中文名**，不随书名变化。分卷大纲不是顶层文件，而是 `分卷大纲/` 下
  一卷一个文件；章节同理，一章两个文件。
- 分卷文件：`分卷大纲/第{卷号}卷.md`，**只带卷号、不补零、不带卷名**。卷名改了文件名不动；
  章节才靠改名，这是刻意的差别：连载中改卷名比改章名频繁得多。
- 章节大纲文件：`章节大纲/第{卷号}卷.md`，同样只带卷号；未排卷的章节进 `章节大纲/未分卷.md`。
  表里的「卷」列才是归属，文件名只是它的落点：一行从第 2 卷改到第 1 卷，它就换文件。
- 章节文件：`第{章号补零到 3 位}章-{净化后的标题}.md`；标题为空时 `第001章.md`。
  细纲文件在同名后加 `.细纲`，即 `第001章-山门.细纲.md`。
- 标题净化：去掉 `/ \ : * ? " < > |`、控制字符、首尾空白与点号；截断到 40 字。
- **稳定键是 `id`（slug），不是文件名**。`id` 写在 frontmatter 里，所以改标题导致的
  文件改名可以恢复：索引按 `id` 定位，读目录时按 frontmatter 的 `id` 认领文件。
- 章号或标题变化时，工具负责 `rename` 文件并更新索引；`章节大纲.md` 同步刷新。
- `竞品拆解.md` 是唯一"缺失不等于空"的顶层文件：在它存在之前录入的竞品拆解留在
  `novel.json` 里，读取时以文件为准、文件无条目则回退到元数据，避免研究资料丢失。

### 2.2 章节文件规模说明

1000 章 = 2000 个章节文件，外加每卷一个分卷大纲文件与一个章节大纲文件。**版本 5 已完成**按卷
拆分 `章节大纲/第1卷.md`（4.0 的说明在此兑现）：索引里的 `chapterPlans` 是「卷号 → 文件」的
列表，读取按它驱动，不假设只有一个文件。

## 3. 文件格式

统一形态：**YAML frontmatter（机器读）+ Markdown 正文（人读）**。解析器只依赖
"frontmatter + `##` 小节 + ```yaml 块 + 表格"这四样，不做自由文本推断。

### 3.1 `全书大纲.md`

```markdown
---
fullOutlineDone: false
updatedAt: 2026-09-13T14:20:34.921Z
---

# 全书大纲

## 一句话

（logline）

## 故事六要素

### 时间

（时代/时段、跨多久、关键时间节点）

### 地点

（主要地图/场景，空间如何转换）

### 起因

（故事为什么开始）

### 经过

（冲突怎么升级）

### 结果

（故事怎么收束）

## 金手指

### 名称

（读者会记住的名字）

### 归属

（人物 id 或姓名）

### 规则

（怎么运转、能做什么）

### 代价

（每次使用付出什么）

### 限制

（做不到什么）

### 成长曲线

（从初始形态到最终形态）

### 首次亮相

（读者第一次看到它的章）

## 完整大纲

（fullOutline —— 3.4 新增：三幕主线、核心剧情走向、全局伏笔、大高潮节点、终极冲突、
结局框架、全书钩子体系。篇幅目标 ≈ 总字数 ÷ 100，可用 novel_plan 的 targetWords 覆盖）

## 三幕

1. （第一幕）
2. （第二幕）
3. （第三幕）

## 最小可行大纲

（minimal）
```

解析：`## 一句话` / `## 最小可行大纲` 取其后正文；`## 三幕` 取有序列表项（保持顺序，
允许 1 项以上，不强制恰好 3 项——SOP 说三幕，但工具不因此拒绝）。

`## 故事六要素` 与 `## 金手指` 是 3.9 新增的两块：前者五个 `###`（时间/地点/起因/经过/结果，
人物读自 `人物设定.md`，不在此重复），后者七个 `###`（名称/归属/规则/代价/限制/成长曲线/首次亮相）。
两块都用与 `## 叙事骨架` 相同的 `###` 方言；缺项由 `storyElementGaps` / `cheatGaps` 报出，
`novel_plan operation="outline"` / `operation="cheat"` 写入。

### 3.2 `人物设定.md` / `3.3 世界观设定.md`

一个条目 = 一个 `## 名称` 节 + 紧随其后的 ```yaml 块 + 其余正文（长描述）。

````markdown
# 人物设定

## 林越

```yaml
id: lin-yue
role: protagonist
scope: main
goal: 上山问清父亲的死因
fear: 发现父亲确实背叛了师门
obsession: 断剑不离手
weakness: 受不得激
camp: protagonist-camp
relations: 与掌门有杀父疑云；与守门弟子有一面之缘
```

十六岁，瘦，左手虎口有旧疤……

## 守门弟子

```yaml
id: shoumen-dizi
role: gatekeeper
scope: volume
goal: 拦住上山的人
personality: 死板，认规矩不认人
voice: 一句话不问第二遍
```

## 挑担老汉

```yaml
id: tiaodan-laohan
scope: cameo
volume: 2
firstAppearance: 第12章
```

在山门口问路，问完就走了。
````

- `id` 缺失时按标题 slug 补；`id` 重复时**报错**（不猜）。文件按档排序（主要角色在前、路人在后），
  便于人读。
- 人物 yaml 键：`id` `role` `scope` `volume` `firstAppearance` `exit` `goal` `personality` `voice`
  `fear` `obsession` `weakness` `camp` `relations` `growthArc` `notes` `description`（可选）。其余正文拼进
  `description`。`relations` 是 3.9 新增：主要角色未写会被 `castRelationGaps` 点名，但不计欠账。
- **`scope` 决定这一条欠什么**（`castGaps`/`castDebt`）：
  - `main` — 主角/反派/核心伙伴：`role` `goal` `personality` `voice`，另加 `fear` `obsession`
    `weakness` `growthArc`；
  - `volume` — 一张地图或一卷内反复出现、或有台词的配角：`role` `goal` `personality` `voice`；
  - `cameo` — 一次性路人：`description`（他是谁）与 `firstAppearance`（首次出场章），
    并要求 `description` 或正文有一句说明。
  - **省略 `scope` 时按 `role` 判**：主角型角色算 `main`，其余算 `volume`——与 3.8 之前的要求
    完全一致，老文件不需要迁移。写了三档之外的值不会猜：按同样的 role 规则兜底，并由
    `kind="review"` 点名。
  - 路人缺项由 `kind="review"` 单独报（「路人登记缺项」），**不计入人物欠账**：看板人设卡、
    人设层的 `discuss`/`confirm`、`novel_status` 的「人物丰满度」都用只算非路人的 `castDebt`。
- `volume` / `firstAppearance` / `exit` 是给"只在一个地图里出现"的路人用的登记字段：
  按卷查人（卷号可由 `firstAppearance` 的章号在章节表里推出，不必重复填）、
  以及防止"第 2 卷死掉的人第 4 卷又走进来"。
- 世界观 yaml 键：`id` `kind`（`place|faction|power-system|item|history|rule`）`cost` `limits`
  `parent` `level` `volume` `relations` `name`（可选，缺省用标题）。其余正文拼进 `detail`。
  `parent`/`level`/`volume` 是 3.9 新增的分层字段：父子包含、层级（1 凡界/2 宗门/3 灵界…）、
  第几卷起出现；悬空 parent、自指与未知 kind 由 `worldStructureGaps` 报出。
- **代价与限制只对规则型条目是硬要求**：`rule`/`power-system`（以及缺省 `note`）缺 `cost`/`limits`
  由 `worldGaps` 报缺口；`place`/`faction`/`item`/`history` 只要求 `detail`。

### 3.4 `分卷大纲/第1卷.md`（版本 4 起：一卷一文件）

````markdown
---
number: 1
title: 山门
goal: 林越拜入山门并立住脚
conflict: 守门弟子与长老的刁难
climax: 试剑台上断剑认主
endHook: 钟声之后，山门后山传来父亲的剑鸣
chapters: [1, 30]
---

# 第 1 卷 山门

## 卷内节奏

（detail —— 卷内节奏与阶段推进，篇幅目标 ≈ 本卷字数 ÷ 50）

## 本卷梗概

（3.5 的七个叙事要素，各自一个 `##`）
````

- **文件就是这一卷**：标量写在 frontmatter 而不是 ```yaml 块里，标题是 `# 第 N 卷 卷名`。
- `number` 必填且为正整数，也是文件名；`chapters` 为闭区间数组，缺省 `[]`（该卷章数未定）。
- 卷内节奏写在 `## 卷内节奏`；七个叙事要素各写一个 `##`。作者另加的 `##` 小节按文件顺序并回
  `detail`，不丢内容；标题下方、第一个 `##` 之前的散文同样算 `detail`。
- v3 的 `分卷大纲.md`（多条目合集）只由**迁移**读取：`parseVolumeCollectionFile()`。
  迁移把它拆成一卷一个文件后删除原文件，先写新文件、后删旧文件。

### 3.5 `章节大纲/第N卷.md`（版本 5 起：一章一行的表按卷分文件）

两个固定表格，**表格是这些列的唯一归属**（§4）。一个文件只放属于这一卷的行：

```markdown
# 第 1 卷 · 章节大纲

## 章节表

| 章 | 标题 | 卷 | 目标字数 | 一句话 | 梗概 |
|---|---|---|---|---|---|
| 1 | 山门 | 1 | 3000 | 林越抵达山门 | 抵达山门 |

## 情绪节拍表

| 章 | 类型 | 一句话 |
|---|---|---|
| 1 | tension | 被守门弟子拦下 |
```

- 解析：按 `## 章节表` / `## 情绪节拍表` 定位，跳过分隔行；单元格内的 `|` 用 `\|` 转义。
- 类型取值沿用 `BEAT_KINDS`（`shuang|sweet|burn|tension|info|turn`）。
- 章号在本文件内重复：**报错**；在两个文件之间重复（同一章被排进两卷）：**报错并指名两个文件**
  ——项目对同一章说了两句话时，读取不是猜的地方。
- 哪个文件归哪一卷：表里的「卷」列。节拍跟它落在的那一章走：那一章还没排卷（甚至还没建章）时，
  节拍进 `未分卷.md`，等它被排进某卷后自己挪过去。
- 一行也没有、且没有节拍的卷**不生成文件**。

### 3.5.1 `章节大纲.md`（全书层）

```markdown
# 章节大纲

章节表（章号、标题、所属卷、目标字数、一句话、梗概）与情绪节拍表按卷分开存放，
一卷一个文件，文件名即卷号；本文件只保留全书共用的开篇工程清单与这份索引。

## 分卷章节表

- 第 1 卷：第 1–40 章（共 40 章）→ 章节大纲/第1卷.md
- 第 2 卷：第 41–80 章（共 40 章）→ 章节大纲/第2卷.md
- 未分卷：第 81–83 章（共 3 章）→ 章节大纲/未分卷.md

## 开篇工程清单

- [ ] chapter-1-conflict-300（第 1 章前 300 字出现冲突）
```

- `## 分卷章节表` 是**派生**的：每卷的文件路径与章号区间由状态算出，每次写入重排，人不填。
- `## 开篇工程清单` 是全书共用的（`done` 决定阶段二门禁），它的兜底仍在 `novel.json` 的
  `opening`：文件里有这一节就以文件为准。
- 本文件里若出现**有行的** `## 章节表` 或 `## 情绪节拍表`：**报错**（那几行没有读者，
  静默忽略等于让计划悄悄失效），错误信息给出它们该去的目录。空表（只有表头）容忍，
  那是刚拆分完的样子。

### 3.8 `竞品拆解.md`（3.4 新增）

与 `人物设定.md` / `世界观设定.md` 同形：一本同榜书一个 `##` 小节，小节标题是书名，
下面一个 ```yaml 块带全部字段。竞品研究是要反复回看的资料，所以它必须落在作者能打开的
文件里，而不是只存在 `novel.json`。

````markdown
# 竞品拆解

## 断剑

```yaml
id: 断剑
title: 断剑
tags: ["玄幻", "热血"]
blurb: 少年持断剑上山。
openingEvent: 第一章：山门前的拦路
goldenFinger: 断剑认主
protagonistDesire: 查明父亲死因
antagonistMotive: 长老要压住旧案
shuangFrequency: 每 3 章一次小爽点
emotionCurve: 压抑—抬头—被认可
paywallPoint: 第 30 章试剑台
chapterHooks: 章末必有未答之问
commentKeywords: ["爽", "节奏快"]
takeaway: 开篇三章内必须给一次小胜
```
````

- 十四个键全在 ```yaml 块里，reader 与 writer 共用同一份键表（`COMPETITOR_KEYS`），
  否则写出去而读不回来的字段会在下一次编辑时静默丢失。
- ```yaml 块之后的散文并入 `takeaway`：那是在条目旁边手写的批注，也是研究。
- 重复 `id` 是**报错**，不是后者覆盖——`id` 是索引与寻址的键。
- 文件不存在或没有条目时，`competitors[]` 回退到 `novel.json` 里早先的记录。

- `status` 取值沿用 `CHAPTER_STATUSES`（`planned|drafting|revised|final`）。
- **`wordCount` 是派生值**：工具读入时按正文重算，写文件时按重算结果回填；人不填也不影响。
  人若填了错值，以重算为准（不做"文件为准"的例外——它是派生量，不是内容）。

## 6. 读 / 写路径

### 6.1 读

```
store.read()
  → 读 novel.json（版本守卫用）
  → 按 index 读各 Markdown 文件；hash 未变的文件用上次解析结果（进程内缓存）
  → 组装 NovelState（core 的结构体）
  → 若某文件语法坏：抛 NovelStoreError，消息里带上文件路径与解析器的具体抱怨
```

- 索引缺失/过期（例如目录里有索引未登记的文件）：**扫描一次目录**按 frontmatter `id`
  认领文件，补进索引并回写元数据；孤儿文件（无 frontmatter id）报 warning，不删。
- 人在编辑器里新增一章文件：下次读取时被认领（这是"文件为准"的自然结果）。

### 6.2 写

```
store.update(mutate)
  → 读（§6.1）
  → next = mutate(state)
  → 按 §4 归属做**结构化 diff**，得出需要写的文件集合
  → 逐个写入（每个文件写前重新 stat + 比对 hash；不一致就重新读入并重放该字段……
     本次实现取简化：直接以 next 覆盖，因为策略是"文件为准"且在同一个 update 内
     的并发窗口极小）
  → 写 novel.json（元数据 + 刷新索引/哈希，一次 replaceIfVersion）
  → 任何一步失败：抛 NovelConflictError/NovelStoreError，消息里列出**已写成功**与
     **未写**的文件清单
```

- 写入顺序：内容文件（大纲/设定/章节）→ 元数据。理由是元数据里的索引是"指路牌"，
  宁可短时间指向旧内容，也不要指向不存在的文件。
- 章节标题/章号变化 → 内容写新文件 + 删旧文件 + 更新索引（`rename` 优先，失败再 copy+delete）。

### 6.3 目录卫生

- 工具**只**写 §2 树里的文件；不写临时文件、不写锁文件。
- 派生文件（`manuscript.md`、`templates/*.json`、`reviews/*.md`）行为不变。

## 7. 迁移

1. 读到 `schemaVersion: 2`（内容仍在 JSON 里）：
   - **先备份**：把原文写到 `.novel/novel.v2.backup.json`（已存在则不覆盖）。
   - 按 §2/§3 生成全部 Markdown 文件。
   - 生成当前版本的元数据（含索引与哈希）——v2 直接升到 v5——写回 `novel.json`。
   - 输出一行迁移报告（生成了哪些文件、章节数）。
2. 读到 `schemaVersion: 1`：先按现有 `migrateV1` 升到 2，再走上面的路径。
3. 读到 `schemaVersion: 3`：内容已在文件里，只有分卷还挤在 `分卷大纲.md`。
   - 读出 `index.volumeFile` 指向的合集，按 §3.4 拆成一卷一个文件并写入；
   - **新文件写完之后**才删除合集，中断则下次读取重跑；
   - 索引改写成 `volumeDir` + 每卷 `file`/`hash`；接着按第 4 条把章节表也拆掉（同一次读取），
     文档写成 v5。没有合集文件时跳过这一半，只把索引形态升上去。不备份 `novel.json`：
     这次迁移不删文档里的任何字段，卷内容在删掉合集前已经完整落到新文件里。
4. 读到 `schemaVersion: 4`：分卷已经是「一卷一文件」，但章节表与情绪节拍表还与开篇清单挤在
   `章节大纲.md` 里（版本 5 之前的样子）。
   - 按「卷」列把章节表与节拍表拆成 `章节大纲/第N卷.md`（未排卷的进 `未分卷.md`），节拍跟它
     落在的那一章走；
   - **新文件写完之后**才改写 `章节大纲.md`：只留开篇工程清单与一份各卷索引；
   - 索引加上 `chapterPlanDir` + `chapterPlans`，文档写成 v5。中断了下次读取重跑：拆分读的是
     原文件里的表，而已经写出的分卷文件会由目录认领接回来。表已经是空的（没有行也没有节拍）
     就不拆、也不改原文件，只升索引形态。
   - 读到 v3 的文档会**先拆分卷合集、再拆章节表**，一次读取完成两件事。
5. 读到 `schemaVersion: 5`：正常读取。
6. 备份文件永远保留（人的草稿不能因为一次升级消失）。

## 9. 必须补的测试

- **往返**：每个文件 结构体 → Markdown → 结构体，字段全等（含空字段、含 `|`、含多行正文、
  含中文标点）。
- **frontmatter 边界**：空文件、只有 frontmatter、缺 frontmatter、YAML 缩进错、
  `chapters: [1, 30]` 与 `chapters:\n  - 1` 两种写法都要吃下。
- **表格**：单元格含 `\|`、含多行、缺列 → 报错而不是错位。
- **id 重复 / 章号重复** → 报错。
- **外部改动采纳**：手改 `章节/第001章-山门.细纲.md` 的 `## 章末钩子` → 下次 `novel_write`
  的兑现回报按新钩子判定。
- **语法坏掉**：把正文文件 frontmatter 写坏 → 工具**报错并指名文件**，且**不改动该文件**。
- **迁移**：v2 文档 → 生成全部文件 + 备份 + 当前版本元数据；再读一次幂等。
  v3 文档 → 合集拆成一卷一个文件、合集被删除、索引写成 `volumeDir` + `volumes`；再读一次幂等；
  没有合集文件的 v3 文档不凭空造出卷。
  v4 文档 → 章节表与节拍表按「卷」列拆成一卷一个文件、`章节大纲.md` 只剩清单与索引；再读一次幂等；
  表本来就是空的时不造文件。
- **分卷**：一卷一文件；改第 2 卷不动第 1 卷的字节；删掉某一卷后它的文件被删；手写放进
  `分卷大纲/第9卷.md` 的文件下次读取被认领。
- **章节大纲**：一卷一文件；改第 3 章不动第 1 卷文件的字节；某一卷的行搬空后它的文件被删；
  已存在的章被手写表补全列；同一章被两个文件排到两卷 → 报错并指名两个文件；
  表里全是还没建的章 → 提示先建章、原文件保留、再读一次不产生任何写入。
- **重命名**：改章节标题 → 文件改名、旧文件消失、索引指向新路径、`章节大纲.md` 同步。
- **现有 187 个 spec**：逐个改断言目标（不是删测试）；SOP 流程的端到端用例必须继续全绿。

## 10. 与既有承诺的关系（不要打破的东西）

1. **工具仍不改写正文**：`novel_review` 的改写稿仍只落 `.novel/reviews/*.md`；只有
   `novel_write` 能写 `章节/*.md`。
2. **阈值仍只认元数据**：`readings`/`iterations`/`evaluations`/`launchDecisions` 留在
   `novel.json`，`novel_assess` 的裁决不因为这次改造而变成读 Markdown。
3. **越界保护不变**：所有路径仍由 `NovelStore.contain()` 做路径算术判定，拒绝逃出工作区根。
4. **模型草稿不是事实**：`novel_review` 的 `save=true` 语义不变，只是落点是新文件。
